Storing a password is not the same as hashing one

A cryptographic hash is designed to be fast. That is exactly the wrong property when the thing you are protecting is a password. Below, alice and bob pick the same password — the way real users do.

Plain SHA-256

PBKDF2 is the weakest of the four acceptable answers — Argon2id, then scrypt, then bcrypt, then PBKDF2. It is here because your browser can run it natively through Web Crypto with no dependencies. Argon2id is memory-hard, which is what makes GPU cracking genuinely expensive rather than merely slow.

Which function, and what do the numbers mean?

The number in a hash function's name is its output size in bits. Divide by 8 for bytes, or by 4 for the hex characters you actually see on screen. That is the whole trick: SHA-256 → 32 bytes → 64 hex characters.

Building something new

SHA-256. Twenty years of analysis, hardware acceleration on almost every CPU, and support in every language you will ever touch. SHA-512 when you want more margin.

Storing passwords

Never a plain hash. Argon2id first, then scrypt, then bcrypt, then PBKDF2. The goal is to make each guess expensive, not to make the digest short.

Verifying old data

Match whatever produced it — but do not sign anything new with MD5 or SHA-1. Both have working, published collision attacks.
